# AI Hackathon Backend API

This document describes the API implemented by the current Google Apps Script backend. It is generated from the current `app-script/` code and does not describe unimplemented functionality.

## Endpoint

Deploy the Apps Script project as a web app and use the deployment URL:

```text
https://script.google.com/macros/s/DEPLOYMENT_ID/exec
```

`DEPLOYMENT_ID` is a placeholder. The deployed URL is not stored in this repository.

- `GET` returns a health response.
- `POST` accepts a JSON request body.
- All POST responses use JSON.

### GET health check

```json
{
  "success": true,
  "service": "AI Hackathon API",
  "status": "ONLINE"
}
```

### POST request envelope

Every POST request requires an `action` field. Protected actions also require `idToken`.

```json
{
  "action": "ACTION_NAME",
  "idToken": "GOOGLE_ID_TOKEN",
  "data": {}
}
```

Successful responses normally use:

```json
{
  "success": true,
  "data": {}
}
```

Failures use:

```json
{
  "success": false,
  "error": "Human-readable message",
  "code": "ERROR_CODE"
}
```

Invalid JSON, a missing body, a missing action, and unknown actions are rejected by the top-level router.

## Authentication and authorization

The backend sends the supplied Google ID token to Google's `tokeninfo` endpoint. It validates:

- Token presence.
- The OAuth audience against the configured Google client ID.
- A present email address.
- Google email verification.
- The `bitsathy.ac.in` email domain.
- The hosted domain when the token supplies `hd`.
- Token expiration when `expires_in` is supplied.

The token is never returned in an API response. The backend uses the verified normalized email, and returns no token-derived role supplied by the client.

Participant actions use `requireTeamLeader()`. In the current implementation, this means the verified email must match `LeaderEmail` on an `ACTIVE` Teams row. Member emails are not available in the current Teams schema, so a member account cannot use these participant APIs unless it is also recorded as a team leader.

Admin actions use `requireAdmin()`. The verified email must have an `ACTIVE` row in the Admins sheet. A missing row returns `ADMIN_NOT_FOUND`; a disabled row returns `ADMIN_DISABLED`. A client-provided `role`, email, TeamID, or admin flag is not trusted.

## Shared business rules

- Team IDs are generated by the backend in the form `BIT-AI-001`.
- Problem IDs are generated by the backend per domain in the form `AGR-01`.
- Only `LOCKED` selections count toward domain capacity.
- `CANCELLED` selections do not consume capacity and do not keep a problem locked.
- A `LOCKED` problem is excluded from participant availability.
- A team may have only one locked selection.
- A problem may have only one locked selection.
- Team and problem selection writes use Apps Script `ScriptLock`.
- Existing locked selections are not deleted when teams, problems, or domains are disabled.

## Participant actions

### REGISTER_TEAM

**Authentication:** Required. The verified Google account becomes `LeaderEmail`.

**Requirement:** Authenticated account. The request must contain valid team data. `leaderEmail` in the request is overwritten by the verified token email and is not trusted.

**Request:**

```json
{
  "action": "REGISTER_TEAM",
  "idToken": "GOOGLE_ID_TOKEN",
  "data": {
    "teamName": "Team Alpha",
    "leaderName": "Asha Kumar",
    "leaderRegisterNumber": "BIT001",
    "leaderDepartment": "CSE",
    "members": [
      {
        "name": "Ravi Das",
        "registerNumber": "BIT002",
        "department": "CSE"
      }
    ]
  }
}
```

`members` may contain at most four additional members. Names, register numbers, and departments are required for each supplied member. Register numbers are normalized to uppercase.

**Success response:**

```json
{
  "success": true,
  "data": {
    "teamId": "BIT-AI-001"
  }
}
```

**Example:** The request above creates an `ACTIVE` team and writes the server timestamp to `CreatedAt`.

**Possible errors:** `AUTH_REQUIRED`, `INVALID_TOKEN`, `INVALID_AUDIENCE`, `EMAIL_NOT_VERIFIED`, `COLLEGE_EMAIL_REQUIRED`, `INVALID_TEAM_DATA` (when surfaced by an admin wrapper), `TEAM_ALREADY_REGISTERED`, `DUPLICATE_REGISTER_NUMBER`, and `INTERNAL_ERROR` for uncategorized validation errors in the current registration path.

### GET_DOMAINS

**Authentication:** Required. The authenticated account must be the leader of an `ACTIVE` team.

**Request:**

```json
{
  "action": "GET_DOMAINS",
  "idToken": "GOOGLE_ID_TOKEN"
}
```

**Success response:**

```json
{
  "success": true,
  "data": [
    {
      "domainId": "AGR",
      "domainName": "Agriculture & Rural Development",
      "maximumTeams": 12,
      "currentLockedTeams": 10,
      "remainingCapacity": 2,
      "available": true
    }
  ]
}
```

Only `ACTIVE` domains are returned. Capacity is calculated from `Selections` rows whose status is `LOCKED`; remaining capacity is never below zero.

**Possible errors:** `AUTH_REQUIRED`, `INVALID_TOKEN`, `INVALID_AUDIENCE`, `EMAIL_NOT_VERIFIED`, `COLLEGE_EMAIL_REQUIRED`, `TEAM_NOT_FOUND`, `TEAM_DISABLED`, and `INTERNAL_ERROR`.

### GET_PROBLEMS

**Authentication:** Required. The authenticated account must be the leader of an `ACTIVE` team.

**Request:**

```json
{
  "action": "GET_PROBLEMS",
  "idToken": "GOOGLE_ID_TOKEN",
  "data": {
    "domainId": "AGR"
  }
}
```

**Success response:**

```json
{
  "success": true,
  "data": [
    {
      "PSID": "AGR-03",
      "Title": "Rural Water Planning",
      "Description": "Problem description",
      "WhatToBuild": "Build a planning tool",
      "DomainID": "AGR"
    }
  ]
}
```

The server checks, in order, the authenticated active team, domain existence and status, release time, selection status, and domain capacity. It returns only active, unlocked problems from the requested domain.

Before release, no problem records or problem fields are returned. The response is instead:

```json
{
  "success": false,
  "error": "Problem statements have not been released yet.",
  "code": "PROBLEMS_NOT_RELEASED"
}
```

**Possible errors:** `AUTH_REQUIRED`, `INVALID_TOKEN`, `INVALID_AUDIENCE`, `EMAIL_NOT_VERIFIED`, `COLLEGE_EMAIL_REQUIRED`, `TEAM_NOT_FOUND`, `TEAM_DISABLED`, `DOMAIN_NOT_FOUND`, `DOMAIN_DISABLED`, `PROBLEMS_NOT_RELEASED`, `SELECTION_CLOSED`, `DOMAIN_CAPACITY_REACHED`, and `INTERNAL_ERROR`.

### SELECT_PROBLEM

**Authentication:** Required. The authenticated account must be the leader of an `ACTIVE` team. The backend determines the TeamID from the verified email; TeamID is not accepted as an authorization field.

**Request:**

```json
{
  "action": "SELECT_PROBLEM",
  "idToken": "GOOGLE_ID_TOKEN",
  "data": {
    "domainId": "AGR",
    "psId": "AGR-03"
  }
}
```

**Success response:**

```json
{
  "success": true,
  "data": {
    "teamId": "BIT-AI-001",
    "domainId": "AGR",
    "psId": "AGR-03",
    "selectedAt": "2026-09-09T10:30:00.000Z",
    "status": "LOCKED",
    "problem": {
      "title": "Rural Water Planning",
      "description": "Problem description",
      "whatToBuild": "Build a planning tool"
    }
  }
}
```

The complete critical transaction runs under `LockService.getScriptLock()`. While holding the lock, the backend re-reads the active team, domain, problem, release state, selection state, existing team/problem locks, and domain capacity before appending the `LOCKED` Selections row.

**Possible errors:** `AUTH_REQUIRED`, `INVALID_TOKEN`, `INVALID_AUDIENCE`, `EMAIL_NOT_VERIFIED`, `COLLEGE_EMAIL_REQUIRED`, `TEAM_NOT_FOUND`, `TEAM_DISABLED`, `INVALID_REQUEST`, `SELECTION_CLOSED`, `PROBLEMS_NOT_RELEASED`, `DOMAIN_NOT_FOUND`, `DOMAIN_DISABLED`, `PROBLEM_NOT_FOUND`, `PROBLEM_DISABLED`, `PROBLEM_DOMAIN_MISMATCH`, `TEAM_ALREADY_HAS_SELECTION`, `PROBLEM_ALREADY_LOCKED`, `DOMAIN_CAPACITY_REACHED`, and `INTERNAL_ERROR`.

## Release behavior

The backend reads `ProblemReleaseDate` and `ProblemReleaseTime` from Config. Values may be Sheets Date objects or supported strings. They are parsed using the Apps Script project timezone `Asia/Kolkata` and compared with Apps Script server time.

`ProblemReleaseOverride = TRUE` makes `isProblemReleased()` return true regardless of the configured date and time. Participant `GET_PROBLEMS` and `SELECT_PROBLEM` never return or lock problem data before release.

Admin `ADMIN_GET_PROBLEMS` intentionally returns all problem records, including disabled and unreleased problems, because it is admin-only. This is an implementation difference from participant release protection and should be considered when designing admin access policy.

## Selection and capacity behavior

A successful selection appends this Selections row:

```text
TeamID | DomainID | PSID | SelectedAt | LOCKED
```

The row is authoritative. `SELECT_PROBLEM` checks all critical conditions while holding a script lock, so simultaneous selection requests cannot both lock the same PSID or exceed domain capacity under the same Apps Script deployment.

Only rows with `Status = LOCKED` count toward `currentLockedTeams` and capacity. `CANCELLED` rows are retained historically but do not count and do not keep a problem locked.

## Frontend security rules

- Send the Google ID token only in the request body as `idToken`.
- Never send an ID token back to the browser from the backend response.
- Do not treat client email, role, TeamID, availability, capacity, release state, or selection state as authoritative.
- Do not embed problem data in frontend static files or expose it before `GET_PROBLEMS` succeeds after release.
- Use the authenticated leader account for participant actions; the backend resolves the team from verified identity.
- Treat every failure response as `{ success: false, error, code }`.
- Do not assume a successful domain display means a problem is still available; availability is rechecked on selection.
- Keep OAuth client secrets out of frontend requests. The public client ID is used only for Google authentication configuration.

## Current implementation differences and limitations

- Participant authorization currently supports authenticated team leaders only because the Teams sheet has `LeaderEmail` but no member-email columns.
- Registration validation errors from the participant `REGISTER_TEAM` path can currently fall through to `INTERNAL_ERROR` rather than a more specific validation code.
- `ADMIN_RELEASE_NOW` persists its override and has no reset action.
- Admin problem listing intentionally bypasses participant release filtering and exposes problem content to authorized admins.
- The repository does not contain a deployed Apps Script URL, so the endpoint above remains a placeholder.
